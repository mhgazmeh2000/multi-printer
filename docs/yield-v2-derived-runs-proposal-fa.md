# پیشنهاد برای تصویب: مرزهای تراکنشیِ تاریخچهٔ Yield

**وضعیت به‌روزشده: نمونهٔ محلی مرحلهٔ ۱ با تأیید مالک ساخته و ارزیابی شد؛
مجوز تغییر کپی ویندوز، migration کاربردی یا تولید هنوز داده نشده است.**
نتیجهٔ نمونه در `yield-v2-derived-runs-stage1-fa.md` آمده است. متن زیر قرارداد و
پیشنهاد اولیه را نگه می‌دارد؛ معیارهای پیشنهادی آن SLA تولیدِ تصویب‌شده نیستند.

این سند پیشنهاد مرحلهٔ بعد پس از بسته‌شدن دور محدود SQL است. نتیجهٔ آن دور در
`yield-v2-performance-gate-fa.md` آمده است: اصلاح‌های کوچک بهبود کافی ندادند،
آزمون واقعی PR17 در کپی ویندوز به timeout خورد و برابری دقیق روی کپی واقعی
هنوز ثابت نشده است. هدف این طرح حذف محاسبهٔ دوبارهٔ مرزهای کل تاریخچه از مسیر
خواندن است، نه تغییر تخمین‌گر، حذف تاریخچه یا دست‌کاری نتایج.

## ۱. قرارداد غیرقابل‌تغییر

- جدول `toner_snapshots_v2` مرجع حقیقت باقی می‌ماند.
- slot از `(printer_ip, LOWER(color))` تاریخچه تعیین می‌شود، نه از فهرست
  cartridge_state. تعداد ۵۲ state موجود، تعداد slotهای تاریخی را ثابت نمی‌کند.
- ترتیب زمانی الگوریتم همان `id` است، نه timestamp.
- مرز run دقیقاً مطابق loader فعلی است: نخستین ردیف slot، تغییر signature
  یا rollback شمارنده نسبت به ردیف قبلی همان slot.
- signature PostgreSQL فعلی بدون تقریب، هش یا تغییر normalization حفظ می‌شود:
  toner_level، raw_level، source با NULL→empty، valid، reject_reason با NULL→empty،
  cartridge_key با NULL→empty و فقط حضور/عدم حضور full_color.
- افزایش عادی شمارنده و مقدار full_color با حضور ثابت، خودبه‌خود مرز نیستند.
  مقایسهٔ rollback با NULL نیز باید عین رفتار SQL فعلی بماند.
- آخرین ۴۰۰ run، حداکثر ۸۰۰ endpoint در هر slot، singleton بدون تکرار،
  همان ستون‌ها و ترتیب سراسری id. درخواست limitهای دیگر نیز حفظ می‌شود.
- خواندن مستقیم یک slot و bulk باید معادل باشند. هیچ فرض append-only، TTL،
  cache پردازشی یا invalidation مبتنی بر MAX(id) مجاز نیست.

## ۲. دادهٔ مشتق پیشنهادی

نام‌ها هنوز قراردادی/مفهومی‌اند:

1. **جدول run starts:** برای هر آغاز run، slot، `start_id` و
   `previous_id` یعنی شناسهٔ ردیف قبلی همان slot ذخیره شود.
2. **جدول وضعیت slot:** آخرین id موجود، نسخهٔ نگهداری/سازگاری و اطلاعات لازم
   برای قفل تراکنشی slot. در حالت آماده، هر slot غیرتهیِ تاریخچه نماینده دارد.
3. **ایندکس همسایگی روی دادهٔ اصلی:** `(printer_ip, LOWER(color), id)` برای
   یافتن predecessor/successor دقیق؛ ایندکس run starts نیز روی slot و start_id.

این ایندکس برای پروتکل نگهداری/جست‌وجوی همسایه پیشنهاد می‌شود؛ ادعا نمی‌کنیم
افزودن آن به‌تنهایی کوئری فعلی را سریع می‌کند. آزمایش قبلی چنین نتیجه‌ای نداد.
اندازه، هزینهٔ ساخت و تأثیر نوشتنِ آن باید در کپی اندازه‌گیری شود.

**همهٔ مرزهای تاریخی نگهداری می‌شوند، نه فقط آخرین ۴۰۰ مرز.** در غیر این صورت
با حذف مرزهای جدید، بازیابی صحیح runهای قدیمی ممکن نیست. در بدترین حالت که هر
poll مرز جدید دارد، اندازهٔ جدول مرزها می‌تواند هم‌مرتبهٔ جدول snapshot باشد.

### خواندن پیشنهادی

از ایندکس مرزها، آخرین N آغاز run هر slot خوانده می‌شود. برای جدیدترین run،
آخرین id از وضعیت slot است؛ برای هر run قدیمی‌تر، انتهای آن `previous_id`
مرز جدیدتر است. سپس endpointهای یکتا از جدول اصلی و در همان SQL statement
خوانده و با id مرتب می‌شوند. اطلاعات snapshot در جدول مرزها کپی نمی‌شود تا
ویرایش payload موجب نمایش نسخهٔ کهنه نشود.

در نتیجه مسیر خواندن بر مبنای تعداد slotها و N مرز منتخب خواهد بود؛ نه یک
WindowAgg روی همهٔ snapshotها. این توصیف مسیر دسترسی است، نه تضمین زمان اجرا.
وجود ایندکس صحیح و نبود اسکن کامل باید با actual plan اثبات شود.

## ۳. نگهداری تراکنشی و صحت تغییرات

محل پیشنهادی نگهداری PostgreSQL است، نه صرفاً Python، تا نویسندهٔ SQL بیرون از
برنامه نیز پوشش داده شود. پروتکل اولیه triggerمحور و fail-closed است: خطای
نگهداری نباید اجازه دهد snapshot با نمای مشتق ناسازگار commit شود.

منطق محلی از این خاصیت می‌آید: مرز یک ردیف فقط به خود آن و predecessor آن
وابسته است. اما پیاده‌سازی باید مجموعهٔ درست ردیف‌های متاثر را جمع کند:

| تغییر | موارد لازم برای محاسبهٔ دوباره |
|---|---|
| INSERT یا backfill | ردیف درج‌شده، successor آن و tail slot |
| DELETE | حذف مرزِ ردیف حذف‌شده، successor باقی‌مانده و tail slot |
| UPDATE signature/counter | ردیف تغییرکرده و successor آن |
| تغییر slot یا id | همسایه‌ها و tail در موقعیت قدیم و جدید |
| bulk statement | اجتماع موارد متاثر در تصویر نهایی statement؛ نه فرض ترتیب trigger ردیفی |
| TRUNCATE | خالی‌کردن تراکنشی نمای مشتق یا غیرفعال‌کردن قطعی آن، بدون باقی‌ماندن دادهٔ کهنه |

`previous_id` successor حتی اگر همچنان آغاز run باشد باید اصلاح شود؛ فقط
بازمحاسبهٔ changed کافی نیست. rollback تراکنش باید تغییر اصلی و مشتق را با هم
برگرداند. ویرایش timestamp یا print_total نیز در خروجی از جدول اصلی دیده شود.

### هم‌زمانی؛ شرط اثبات، نه ادعای حل‌شده

- نویسندگان یک slot باید روی یک ردیف پایدار وضعیت slot هماهنگ شوند؛ slotهای
  قدیم/جدید برای تغییر هویت باید در ترتیب ثابت پردازش شوند.
- تنها advisory lock کافی نیست: در REPEATABLE READ ممکن است snapshot نویسنده
  منتظرمانده قدیمی باشد. به‌روزرسانی نسخهٔ ردیف وضعیت و برخورد serialization
  باید مانع commit نمای ناسازگار شود؛ retry کل تراکنش بخشی از قرارداد است.
- ترتیب قفل slot همهٔ deadlockهای قفل ردیف‌های اصلی را حذف نمی‌کند؛ رفتار
  deadlock، rollback و retry جداگانه آزمون می‌شود.
- پس از commit هر نویسنده، خواننده باید دادهٔ اصلی و مشتق سازگار را در یک
  snapshot ببیند. ترکیب چند SELECT مستقل با READ COMMITTED پذیرفته نیست.
- دو نویسندهٔ هم‌زمان، bulk update/delete، جابه‌جایی بین slotها و backfill باید
  با barrierهای آزمون، در READ COMMITTED و REPEATABLE READ آزمایش شوند.
- مسیرهای bypass مثل disable trigger یا replication role باید صریحاً ممنوع یا
  با rebuild و غیرفعال‌کردن نمای مشتق مدیریت شوند. هیچ تضمینی برای bypass خاموش نداریم.

طراحی SQL دقیقِ triggerها و پروتکل هم‌زمانی باید قبل از اتصال به مسیر کاربردی
بازبینی شود. اگر این قراردادها اثبات نشوند، پیاده‌سازی قابل انتشار نیست.

## ۴. ساخت اولیه، rollout و برگشت

1. ابتدا فقط در PostgreSQL محلی موقت: schema آزمایشی، نگهداری و oracle مستقل.
2. سپس با اجازهٔ جداگانه، schema و rebuild فقط در کپی مستقل روی E.
   این بار نوشتن در **کپی آزمایشی** لازم است؛ مجوز SELECTهای قبلی آن را پوشش نمی‌دهد.
3. build با marker «آماده نیست» آغاز شود؛ نسخه، شمارش و سازگاری بررسی و سپس
   به‌طور اتمیک آماده شود. reader نباید دادهٔ نیمه‌ساخته را مصرف کند.
4. برای نخستین build تولید، پیش‌فرض محافظه‌کارانه یک پنجرهٔ توقف کنترل‌شدهٔ
   نویسندگان است. مدت آن باید روی کپی اندازه‌گیری و جداگانه تصویب شود؛ ساخت آنلاین
   بدون وقفه را وعده نمی‌دهیم. هیچ مجوزی برای توقف poller تولید فعلاً وجود ندارد.
5. قابلیت جدید ابتدا خاموش باشد. روشن‌کردن تولید پس از شواهد، PR و تأیید انتشار
   جداگانه است. SQLite در این مرحله loader فعلی را حفظ می‌کند و parity می‌گیرد.
6. در نبود schema/نسخه/وضعیت آمادهٔ معتبر، reader به مسیر قبلی دقیق برگردد؛
   این fallback ممکن است کند باشد، ولی نباید نتیجهٔ کهنه یا ناقص بسازد.
7. برگشت اولیه با خاموش‌کردن مسیر خواندن جدید باشد؛ حذف trigger/schema در تولید
   عملیات جداگانه است. تا وقتی trigger باقی است، هزینهٔ نگهداری نوشتن هم باقی می‌ماند.

## ۵. معیارهای پذیرش و نقطهٔ توقف پیشنهادی

این معیارهای کارایی **پیشنهاد برای تصویب** هستند، نه SLA پذیرفته‌شده یا نتیجهٔ موجود:

- **صحت:** صفر اختلاف در tuple کامل و ترتیب خروجی روی oracle مستقل و کپی واقعی،
  قبل/بعد از تمام mutationها؛ اعداد شمارش و checksum جای آن را نمی‌گیرند.
- **حفظ سازگاری:** آزمون‌های هم‌زمانی و failure/rollback باید پاس شوند؛ هیچ stale
  result مجاز نیست. تست‌های موجود yield، audit، operational و startup نیز حفظ شوند.
- **خواندن:** پیشنهاد هدف loader کامل fleet روی همان کپی: هرکدام از ۵ اجرای
  تکراریِ پس از warm-up حداکثر ۲ ثانیه؛ first-run جداگانه گزارش شود. این ۵ اجرا
  برآورد p95، cold-cache، latency API یا تضمین ETA واقعی نیستند.
- **نوشتن:** p50/p95 زمان تراکنش، throughput، deadlock/retry، WAL و فضای دیسک نسبت
  به baseline در workload یکسان اندازه‌گیری شوند. آستانهٔ مجاز پس از روشن‌شدن
  نرخ واقعی ingestion و قبل از فعال‌سازی توافق شود؛ فعلاً عدد ساختگی تعیین نمی‌شود.
- **عملیات:** rebuild قطع‌شده، restart، marker نسخه، restore و rollback قابلیت
  آزمایش شوند؛ ساخت اولیه و فضای موردنیاز روی E گزارش شوند.

زمان بیش از ۳۰ ثانیهٔ baseline قبلی مجوز افزایش بی‌حد timeout نیست. برای مقایسهٔ
واقعی می‌توان مرجع را slotبهslot، با سقف زمانی و همان snapshot، ارزیابی و خروجی
را بر اساس id سراسری ترکیب کرد. اگر یک slot هم در سقف نگنجد، آزمون باید صریحاً
ناقص اعلام شود و روش مرجع بازبینی شود؛ حذف تاریخچه یا مقایسهٔ فقط tail مجاز نیست.

**قرارداد این مرحله:** یک نمونهٔ پیاده‌سازی، یک دور اصلاح بر اساس آزمون‌ها، سپس
گزارش قبول/رد. عبور از گیت‌ها مجوز خودکار merge یا استقرار نیست. اگر صحت، هزینهٔ
نوشتن یا هدف خواندن پاس نشد، توقف و گزارش محدودیت؛ نه تغییر دامنهٔ بی‌پایان.

## ۶. آیا دادهٔ واقعی بیشتری لازم است؟

برای تصویب این طرح و شروع نمونهٔ محلی، **خیر**. dump جدید، دادهٔ خام، DSN، `.env`،
لاگ خصوصی یا فایل credential لازم نیست. کپی موجود روی E برای گیت واقعی حفظ شود.

برای واقع‌گراترکردن workload، یک گزارش آماری ناشناس از همان کپی مفید است:

- تعداد واقعی slotهای تاریخچه و توزیع تعداد snapshot در هر slot، بدون IP؛
- سهم NULLها، طول متن‌ها و تعریف ایندکس‌های موجود؛
- در صورت امکان با هزینهٔ کنترل‌شده، توزیع طول run و نرخ مرز/rollback؛
  این بخش می‌تواند به window سنگین نیاز داشته باشد و فعلاً نباید کورکورانه اجرا شود.
- نرخ واقعی ingestion از پایش موجود؛ شمارش snapshotها لزوماً نرخ poll یا فشار
  نوشتن را نشان نمی‌دهد، چون ذخیره‌سازی snapshot ممکن است gated باشد.

۴۸ slot در آزمون مصنوعی صرفاً fixture بوده است. برابر بودن تعداد کل ردیف‌ها
با کپی واقعی، توزیع، پهنای ردیف، locality، cache یا سرعت دیسک را یکسان نمی‌کند.
حتی گزارش آماری خوب هم جای آزمون روی کپی واقعی را نمی‌گیرد.

**فعلاً هیچ فرمان تازه‌ای برای سرور لازم نیست.** اگر دامنه تصویب شد، ابتدا نمونه
محلی ساخته شود و سپس فقط گزارش‌های تجمیعی ضروری، با فرمان کامل و امن، درخواست
شود. خروجی خام یا اطلاعات شناسایی‌کننده برای این مرحله درخواست نمی‌شود.
