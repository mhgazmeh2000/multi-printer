# تصمیم گیت کارایی Yield v2 — دور محدود پس از PR17

## نتیجهٔ اجرایی

**آمادهٔ انتشار تأیید نشده است. این دور با نتیجهٔ منفی بسته شد.**

این گزارش جایگزین شواهد قبلیِ صحت الگوریتم نیست و اجازهٔ استقرار، مهاجرت یا
تغییر تنظیمات تولید نمی‌دهد. برای اصلاح‌های آزمایشی زیر هیچ تغییری در
`core/yield_engine.py`، ایندکس‌ها یا migrationها اعمال نشده است.

## شاهد واقعی: کپی مستقل ویندوز

خروجی تحویلی کاربر از profiler فقط-PR17:

- PostgreSQL 17.5، `shared_buffers=128MB`، `work_mem=4MB`، parallel workers per gather برابر ۲.
- SELECT جدید در `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)` پس از **۳۰٫۱۳۵۸ ثانیه**
  به‌طور تأییدشده با `statement_timeout` و SQLSTATE `57014` لغو شد.
- پلن **تخمینی** برای WindowAgg تاریخچه حدود ۲٬۱۲۶٬۱۲۱ ردیف برآورد می‌کند؛
  این عدد تعداد ردیف واقعی پردازش‌شده یا زمان هر گره نیست.
- پلن actual به دست نیامد؛ گلوگاه دقیق زمان اجرا روی ویندوز هنوز ثابت نشده است.
- سرور مستقل آزمایش پس از اجرا با موفقیت خاموش شد.
- مقایسهٔ دقیق خروجی قدیم و جدید روی این کپی هنوز انجام نشده است.
- از این اجرا نمی‌توان سرعت نسبی PR16/PR17، درصد بهبود، کندتر بودن نسخهٔ جدید
  یا آمادگی تولید را نتیجه گرفت. اجرای قبلی baseline نیز لغو شده بود.

## دور محدود محلی: آیا تغییر کوچک SQL کفایت می‌کند؟

دو تغییر کوچک، فقط داخل آزمایشگاه، ارزیابی شدند:

1. **reverse_edges:** محاسبهٔ انتهای run با LAG در ترتیب نزولی، هم‌جهت با SUM رتبه؛
   حذف نیاز به یکی از ترتیب‌های میانی بدون تغییر مرزهای run.
2. **bounded_frame:** قاب صریح `ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING` برای
   پنجرهٔ اولیه؛ LAG/LEAD در هر دو موتور مستقل از قاب هستند.

آزمایشگاه از SQL تابع loader در checkout جاری استفاده می‌کند، ولی برنامه،
settings و `.env` را import نمی‌کند. فقط یک PostgreSQL موقت متعلق به خودش
می‌سازد؛ ورودی DSN ندارد. کلاستر پس از آزمون حذف می‌شود. هیچ اتصال تولیدی،
کپی ویندوز، dump خصوصی یا اطلاعات واقعی وارد این آزمون نشده است.

### تنظیم و داده

- Linux، PostgreSQL **16.2** از بستهٔ اختیاری `pgserver`؛ نه ویندوز و نه PG17.5.
- ۲٬۱۲۶٬۳۰۰ ردیف کاملاً مصنوعی، ۴۸ slot، runهای حدود ۱۰۰ poll، آخرین ۴۰۰ run.
- انواع ستون‌های مورد استفاده مطابق migration 0001: id از نوع BIGINT و شمارنده‌ها،
  درصدها و valid از نوع INTEGER؛ متن‌های fixture کوتاه‌اند و توزیع واقعی را شبیه‌سازی کامل نمی‌کنند.
- shared_buffers برابر 128MB، work_mem برابر 4MB، parallel workers per gather برابر ۲،
  statement_timeout برابر ۳۰ ثانیه.
- فقط PK و ایندکس موجود `(printer_ip, color, timestamp)`؛ بدون ایندکس جدید.
- دو تکرار، با چرخش ترتیب اجرا؛ **آزمون cold-cache، صدک تأخیر یا SLA نیست**.
- اندازه‌گیری با `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)`؛ دریافت خروجی برای برابری
  در SELECTهای جداگانه در همان تراکنش REPEATABLE READ و READ ONLY انجام شد.

### اندازه‌گیری نهایی قابل‌بازتولید

زمان‌ها زمان اجرای گزارش‌شدهٔ PostgreSQL، بر حسب ثانیه هستند؛ نه زمان HTTP/API.

| SQL | تکرار اول | تکرار دوم | ردیف خروجی | برابری دقیقِ ستون‌ها و ترتیب با نسخهٔ جاری |
|---|---:|---:|---:|---|
| جاری PR17 | 7.457 | 6.846 | 38,400 | مرجع |
| reverse_edges | 7.044 | 6.905 | 38,400 | بله |
| bounded_frame | 7.274 | 6.786 | 38,400 | بله |

مجموع temp read/write گزارش‌شده در ریشهٔ پلن برای نسخهٔ جاری و reverse_edges
در هر دو تکرار **۱۹٬۴۴۳ / ۱۹٬۴۹۱ بلوک** بود. برای bounded_frame تکرار دوم
۱۹٬۴۴۱ / ۱۹٬۴۸۹ بود. این شمارنده‌های والد شامل فرزندان هستند و نباید دوباره
با آن‌ها جمع شوند. صرف مشاهدهٔ این اعداد اثبات نمی‌کند علت timeout ویندوز همین است.

**برداشت:** تفاوت‌ها کوچک و متأثر از ترتیب/گرم‌شدن اجرا هستند؛ برتری پایدار
ثابت نشده و هیچ‌کدام مسئلهٔ پردازش تاریخچهٔ کامل را حذف نمی‌کنند. این نتایج
مجوز یک دور دیگر از تست کاربر یا ادعای حل مشکل نیستند. هر دو تغییر برای ورود
به برنامه رد شدند.

## صحت و رگرسیون

`tests/test_yield_query_lab.py` خروجی هر candidate را با یک oracle مستقل پایتونی
به‌صورت tuple کامل و مرتب مقایسه می‌کند، نه فقط شمارش یا checksum. پوشش شامل:

- دادهٔ تهی، singleton، انتهای ثابت طولانی، بیش از ۴۰۰ run و limitهای ۰/۱/۳/۴۰۰/۱۰۰۰؛
- ID گسسته و ترتیب سراسری، slot با رنگ mixed-case، فیلتر مستقیم و گروهی؛
- NULL/empty، source، valid، reject_reason، cartridge identity، حضور full_color؛
- rollback و شمارندهٔ NULL، ویرایش/حذف تاریخی، backfill و انتقال بین slotها؛
- مقایسهٔ PostgreSQL و SQLite با oracle؛ PostgreSQL فقط در دیتابیس آزمایشی
  `printguard_test_*` و با جدول TEMP.

اجرای متمرکز همراه آزمون‌های عملیاتی، audit و startup/fast-pull با PostgreSQL
موقت جداگانه انجام شد: **۴۹ تست پاس، ۴۶۷ subtest پاس، بدون skip یا failure**.
هشدار کلید توسعهٔ پیش‌فرض دیده شد؛ هیچ سرویس برنامه یا محیط تولید اجرا نشد.
smoke ابزار با یک ردیف و سه تکرار نیز برابری دقیق و cleanup موفق داشت.
smoke جداگانه با PGHOSTADDR/PGSERVICE/PGPORT ساختگی هم موفق بود: ابزار همهٔ
متغیرهای ارث‌رسیدهٔ libpq را هنگام آزمایش کنار می‌گذارد و پس از آن برمی‌گرداند،
تا حتی این متغیرها نتوانند اتصال را از کلاستر موقت منحرف کنند.
این پوشش به معنی سبز بودن کل suite یا برابری دادهٔ واقعی ویندوز نیست.

## بازتولید برای توسعه‌دهنده، نه دستور جدید برای سرور کاربر

در محیط توسعهٔ بدون `.env` عملیاتی، پس از نصب وابستگی‌های پروژه و
`psycopg[binary]` و `pgserver` (وابستگی اختیاری ابزار):

```sh
python -m tools.yield_query_lab --rows 2126300 --slots 48 --repeats 2
DB_BACKEND=sqlite PG_DSN='' python -m pytest -q \
  tests/test_yield_query_lab.py tests/test_yield_v2_operational.py \
  tests/test_yield_v2_audit.py tests/test_startup_and_fast_pull.py
```

فرمان دوم به‌طور پیش‌فرض آزمون‌های PostgreSQL را skip می‌کند؛ اجرای ثبت‌شدهٔ
متمرکز با دیتابیس جدید `printguard_test_query_oracle` در کلاستر محلیِ موقت بوده است.
خود ابزار فقط bounded synthetic workload می‌سازد: حداکثر ۳ میلیون ردیف، ۳ تکرار و
۳۰ ثانیه برای هر statement. مدت کل ابزار ممکن است از ۳۰ ثانیه بیشتر باشد.

## نقطهٔ توقف و پیشنهاد بعدی

در محدودهٔ «یک دور اصلاح کوچک و آزمون محلی»، اصلاح قابل‌دفاعی برای انتشار
به دست نیامد. در این مرحله:

- افزایش timeout/work_mem، افزودن ایندکس یا تکرار benchmark روی سرور پیشنهاد اجرایی نیست.
- هیچ PR کاربردی، استقرار، migration، پاک‌سازی تاریخچه یا تغییر تولید انجام نشد.
- گیت انتشار از نظر کارایی و برابری روی کپی واقعی باز نشده است.

اگر مالک ادامهٔ توسعه را تصویب کند، پیشنهاد مشخص یک **بازطراحی جداگانهٔ
نگهداری تراکنشیِ مرزهای run** است، نه یک patch ظاهری دیگر به پنجره‌ها. پیش از
پیاده‌سازی باید طرح صحت آن برای INSERT، backfill، UPDATE/DELETE تاریخی، تغییر
هویت slot، هم‌زمانی چند نویسنده و rebuild/rollback بررسی و تصویب شود. MAX(id)،
TTL یا فرض append-only جای این تضمین‌ها را نمی‌گیرند. این فقط پیشنهاد طراحی است،
نه تصمیم پیاده‌سازی یا اجازهٔ تغییر schema. اگر این دامنه تصویب نشود، وضعیت
صادقانهٔ این گیت «آمادهٔ انتشار نیست» باقی می‌ماند.
