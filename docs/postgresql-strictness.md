# PostgreSQL strictness — چیزهایی که SQLite می‌بخشد و PG نمی‌بخشد

**فاز:** E.0 (مستندسازی) — کار E.0.10. **وضعیت:** فقط مستندات؛ در این فاز هیچ کد/schema تغییر نکرده است.
**مبنای اندازه‌گیری:** شاخه‌ی `phase-c`، تاریخ ۲۰۲۶-۱۰-۰۳؛ روش: grep/AST روی درخت کاری + شمارش دستی، نه حدس.
**دامنه:** ۱۰ جدول (`logs`, `toner_history`, `sensor_readings`, `users`, `printer_counters`,
`cartridge_state`, `cartridge_yield_profiles`, `yield_samples`, `toner_snapshots_v2`, `security_events`)
و ۶۷ روت Flask. لایه‌ی ترجمه: `core/db/` (فاز D) — جزئیات در `docs/db-adapter.md`.

**کلاس‌های خطر:**
- 🔴 **خطای سخت:** PG همان SQL را رد می‌کند (بهترین حالت: زود لو می‌رود).
- 🟡 **تغییر خاموش:** PG می‌پذیرد ولی **معنا/نتیجه فرق می‌کند** (خطرناک‌تر).
- 🟢 **سازگار:** بررسی شد، مشکلی نیست (برای اینکه دوباره کاوش نشود).

---

> **وضعیت (۲۰۲۶-۱۰-۰۴):** جدول ۱۷ ردیفی زیر **تحلیل اولیه** است (محض تصمیم در E.0).
> آنچه پس از اجرای E.4 بر هر ردیف گذشت، در **بند ۷ همین سند** با شمارهٔ کامیت ثبت شده:
> ۱۳ ردیف بسته · ۳ ردیف ⬜ no-action آگاهانه · ۱ ردیف ⏳ موکول به E.6.

## ۲. جزئیات موارد بحرانی

### ۱) `substr(timestamp, 1, 10)` — مرزهای روز — ✅ **رفع شد در E.3.4**

> **وضعیت (۲۰۲۶-۱۰-۰۴):** این خطر **برطرف شد** و کدِ زیر دیگر در مخزن نیست. در
> E.3.4 تجمیع از SQL به پایتون منتقل شد: کوئری فقط ردیف‌های خام را می‌خواند و
> سبد روزانه با `core/time_utils.to_local_day()` (روزِ Asia/Tehran از مقدار UTC/Z)
> و مرز پنجره با `_local_day_start()` ساخته می‌شود. نتیجه: هیچ تابع تاریخِ
> وابسته به backend در SQL نماند، و خطر «بی‌صدا UTC شدن مرز روز» از بین رفت.
> در E.4 فقط باید بازبینی شود که خواندن `timestamp` به‌عنوان `TIMESTAMPTZ` و
> تبدیل آن در پایتون همان نتیجه را بدهد. متن زیر برای حفظ تاریخ تحلیل باقی است.

```sql
-- web/routes/stats.py:24-31 (و همان الگو در :32-39 و :76-83) — حذف‌شده در E.3.4
SELECT substr(timestamp, 1, 10) as day, COALESCE(SUM(pages), 0) as total
FROM logs
WHERE printer_ip = ? AND type = 'PRINT' AND timestamp >= ?
  AND pages IS NOT NULL AND pages > 0
GROUP BY day ORDER BY day
```

- در SQLite، `timestamp` یک متن ISO است و `substr(...,1,10)` یعنی «۱۰ کاراکتر اول» ⇒
  «روزِ **همان متنی که نوشته شده**» (امروز: ساعت محلی تهران؛ پس مرز روز = نیمه‌شب تهران).
- در PG اگر ستون `TIMESTAMPTZ` شود، `substr(timestamptz, 1, 10)` **خطا** می‌دهد (تابع
  روی نوع تاریخ نداریم) ⇒ برنامه به تغییر تن می‌دهد.
- اما اگر کسی «سریع» آن را به `to_char(ts,'YYYY-MM-DD')` یا `ts::date` تبدیل کند،
  نتیجه **بی‌صدا** به مرز روزِ UTC می‌رود ⇒ برای `TZ=Asia/Tehran` تمام سطرهای
  ۰۰:۰۰–۰۳:۳۰ به روز قبل می‌افتند (همان ۳:۳۰ که در D.6 رفع شد).
- **قاعده‌ی فاز E:** هر «روز» باید صریح باشد:

```sql
-- معادل درست در PG (مرز روز به وقت تهران، مثل رفتار امروز)
SELECT date_trunc('day', timestamp AT TIME ZONE 'Asia/Tehran')::date AS day,
       COALESCE(SUM(pages), 0) AS total
...
GROUP BY 1 ORDER BY 1;
```

همین الگو در سه جای دیگر: `web/routes/stats.py:34` (حالت بدون `ip`)،
`web/routes/stats.py:78` (سنسور: `AVG(value)` روی `sensor_readings`).

### ۳) `COLLATE NOCASE` (🔴)

```sql
-- core/database.py:549-556 — فهرست کاربران
ORDER BY
    CASE role WHEN 'admin' THEN 0 WHEN 'manager' THEN 1 ELSE 2 END,
    username COLLATE NOCASE ASC
```
`NOCASE` یک collation **مخصوص SQLite** است (و فقط ASCII را fold می‌کند). PG چنین
نامی ندارد ⇒ خطای «collation ... does not exist». جایگزین: `lower(username)` (ساده و
قابل پیش‌بینی) یا collation مبتنی بر ICU. نکته‌ی پنهان: امروز `Ali` و `ali` در SQLite
یکسان مرتب می‌شوند ولی `نامِ فارسی` fold نمی‌شود؛ در PG ترتیب را collation سرور تعیین
می‌کند ⇒ نتیجه **عوض می‌شود** (نه فقط خطا).

### ۴) ترتیب رشته‌ها و collation (🟡) — ✅ **تصمیم E.6.3: `C` می‌ماند**

| جای | الگو |
|---|---|
| `core/database.py:555` | `username COLLATE NOCASE ASC` |
| `web/routes/import_db.py:123` | `ORDER BY "ip"` (IP رشته‌ای — ترتیب لغوی، نه عددی) |
| `core/yield_engine.py:1233`, `core/yield_engine.py:559` | `ORDER BY printer_ip, color` / `ORDER BY id DESC` |
| `core/database.py:1269` | `ORDER BY printer_ip ASC, timestamp ASC` |
| `web/routes/metrics.py:125` | `ORDER BY printer_ip` |

امروز SQLite بر پایه‌ی بایت‌های UTF-8 مرتب می‌کند؛ PG بر پایه‌ی collation پایگاه‌داده.
برای نام‌های فارسی (`HP-رنگی`، `توشیبا`، `ECS100G Rack`) این دو **یکسان نیستند**.
تصمیم لازم در فاز E: collation سرور (`C` برای بایت‌محور بودنِ قابل‌پیش‌بینی، یا
`ICU`/`fa-IR` برای ترتیب انسانی). هر انتخاب، ترتیب UI را تغییر می‌دهد ⇒ باید در
`docs/cutover-plan.md` صریح ثبت شود.

### ۵) booleanها (🟡)

```sql
-- core/database.py:325-327 (DDL) و :341/:343 (ALTER برای کاربران قدیمی)
is_verified INTEGER NOT NULL DEFAULT 0,
email_verified INTEGER NOT NULL DEFAULT 0,
is_active INTEGER NOT NULL DEFAULT 1,
```
- خواندن‌ها در پایتون تبدیل می‌کنند: `core/database.py:387` (`bool(row[8])`)، `:399`،
  `models.py:40-41`، `web/routes/users.py:91-92`.
- نوشتن: `core/database.py:578` → `UPDATE users SET is_verified = ?, email_verified = ?`.
  اگر ستون در PG `INTEGER` بماند و psycopg مقدار پایتونی `bool` را bind کند، PG
  آن را `true/false` می‌خواند و **خطای نوع** می‌دهد («column is of type integer but
  expression is of type boolean») — یعنی باید یا ستون `BOOLEAN` شود (و خواننده‌ها
  دیگر `bool()` لازم نداشته باشند) یا نویسنده‌ها `int(...)` بفرستند.
- دو ستون boolean دیگر هم همین وضع را دارند: `yield_samples.accepted INTEGER DEFAULT 1`
  (`core/yield_engine.py:284`، مقایسه در `:556` به‌صورت `accepted=1`) و
  `security_events.success INTEGER DEFAULT 0` (`core/security_audit.py:70`).
- تصمیم فاز E: **`BOOLEAN`** برای `is_verified`/`email_verified`/`is_active` و حذف
  تبدیل‌های `bool(row[n])` در مسیر خواندن. (در E.0 هیچ‌کدام تغییر نمی‌کند.)

### ۷) تصریح TimeZone و `TEXT` → `TIMESTAMPTZ` (🟡)

ستون‌های زمانی **همه `TEXT`**‌اند: `core/database.py:245` (`logs.timestamp`)،
`:289`، `:302`، `core/yield_engine.py:300`، `core/security_audit.py:62`،
`users.created_at/updated_at` (`core/database.py:328-329`)، `reset_token_expires`.
مقایسه‌ها لغوی‌اند: `web/routes/stats.py:28/36/80`، `core/database.py:838/879/1197`،
`core/security_audit.py:231`، `core/database.py:1269`.

- امروز «رشته‌ی ISO» با برش متن مقایسه می‌شود و به‌طور تصادفی درست کار می‌کند
  (طول ثابت، ترتیب لغوی = ترتیب زمانی) — به شرط یکنواخت بودن TZ و قالب.
- در PG با `TIMESTAMPTZ` اگر رشته‌ی naive داده شود، **به TimeZone نشست** تفسیر می‌شود
  ⇒ باید `TimeZone=UTC` روی نشست/سرور قفل شود (E.0.1/E.0.2) و writers آگاه-UTC شوند
  (الزام فاز E در `docs/timestamp-consumers.md` §۶).
- محدوده‌ی compare‌های رشته‌ای باید هنگام مهاجرت بازبینی شود: با `TIMESTAMPTZ`،
  مقایسه‌ی `timestamp >= ?` که پارامتر **رشته‌ی محلی** می‌گیرد، ۳:۳۰ جابه‌جا می‌شود.

### ۸) `AUTOINCREMENT` → `IDENTITY` (🔴)

۷ مورد، همه با الگوی `id INTEGER PRIMARY KEY AUTOINCREMENT`:

| فایل | جدول‌ها |
|---|---|
| `core/database.py:242`, `:287`, `:300`, `:317` | `logs`, `toner_history`, `sensor_readings`, `users` |
| `core/security_audit.py:61` | `security_events` |
| `core/yield_engine.py:269`, `:294` | `yield_samples`, `toner_snapshots_v2` |

- `AUTOINCREMENT` کلمه‌ی SQLite است (و جدول داخلی `sqlite_sequence` می‌سازد که
  هرگز «id آزادشده» را بازاستفاده نمی‌کند).
- معادل PG: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`
  (یا `SERIAL`؛ `IDENTITY` استاندارد SQL است).
- نکته‌ی مهاجرت داده: `web/routes/import_db.py:175` ستون `id` را از درج حذف می‌کند
  (`common_cols.remove("id")`) ⇒ sequence دست‌نخورده می‌ماند؛ اما اگر روزی id صریح
  درج شود، `setval` لازم است وگرنه «duplicate key» می‌دهد.

### ۹) `lastrowid` → `RETURNING` (🔴) — **جست‌وجو انجام شد**

کل مخزن (بدون `tests/`) فقط **یک** مصرف زنده دارد:

```python
# core/database.py:508-512
c.execute("INSERT INTO users (...) VALUES (...)", (...))
user_id = cur.lastrowid
```
به‌علاوه فوروارد در adapter: `core/db/connection.py:183-184`
(`lastrowid` → `self._require_cursor(...).lastrowid`). PG هیچ `lastrowid` ندارد ⇒
هر دو باید به `INSERT ... RETURNING id` + `fetchone()[0]` منتقل شوند. اگر adapter
بخواهد ظاهر قدیمی را نگه دارد، باید `RETURNING` را **خودش** به SQL تزریق کند و
نتیجه را در یک slot نگه دارد (طراحی دشوار و پنهان) ⇒ ترجیح فاز E: تغییر دو محل.

### ۱۰) `executemany` (🟡)

```python
# core/database.py:1148-1156 — درج دسته‌ای sensor_readings داخل یک تراکنش
with db_connection(commit=True) as conn:
    conn.executemany("""INSERT INTO sensor_readings (...) VALUES (?, ?, ?, ?, ?, ?, ?)""", rows)
```
- adapter امروز `executemany` را فوروارد می‌کند (`core/db/connection.py:129-136`)؛
  ترجمه‌ی `?`→`%s` در همان لایه لازم است.
- تفاوت رفتاری: در SQLite یک سطر خطادار می‌تواند وسط لیست بایستد و بقیه ادامه یابند؛
  در PG، خطا کل تراکنش را abort می‌کند ⇒ هر «تلورانسِ خطای سطری» باید صریح شود
  (SAVEPOINT per row یا `ON CONFLICT DO NOTHING`).
- همین مسئله برای درج سطربه‌سطر `web/routes/import_db.py:201` (درختاری کامل) صادق
  است؛ در SQLite هر سطر جداگانه try/except می‌شود ولی تراکنش **یکی** است
  (`docs/sqlite-excepts-inventory.md`، مورد UniqueViolation).

### ۱۱) `sqlite_master` و `PRAGMA table_info` (🔴)

```python
web/routes/import_db.py:97   SELECT name FROM sqlite_master WHERE type='table'
web/routes/import_db.py:101  PRAGMA table_info(_q(table))   # helper های _tables()/_columns()
tools/find_insert_or_replace.py:201  PRAGMA table_info(...)
```
PG: `SELECT table_name FROM information_schema.tables WHERE table_schema='public'`
و `SELECT column_name FROM information_schema.columns`. توجه: `import_db.py` یک
**کارِ مهاجرت SQLite→SQLite** است (ورود فایل `.db` دیگر) — در فاز E باید روشن شود
آیا در دنیای PG اصلاً معنا دارد یا باید جدا شود (کاندیدای بازنشستگی، نه ترجمه‌ی
تحت‌اللفظی).

### ۱۲) PRAGMAهای زمان اجرا (🔴)

```python
core/database.py:224   PRAGMA busy_timeout=30000
core/database.py:228   PRAGMA journal_mode=DELETE      # با except برای "locked"
core/database.py:234   PRAGMA synchronous=FULL         # با except برای "locked"
core/db/connection.py:248  PRAGMA busy_timeout=<ms>
```
در PG هیچ‌کدام معنا ندارند (WAL سطح خوشه است، نه سطح پایگاه‌داده). معادل‌ها:
`SET lock_timeout`, `SET statement_timeout`, `SET idle_in_transaction_session_timeout`.
نکته: هندلرهای «locked» (`core/database.py:230/236`) در PG بی‌معنا می‌شوند و باید
به SQLSTATE (`55P03 lock_not_available`, `57014 query_canceled`) نگاشت شوند —
فهرست کامل در `docs/sqlite-excepts-inventory.md` (۳ مورد بررسی پیام ⇒ SQLSTATE).

### ۱۳) `rowid` (🔴)

```python
tools/analyze_old_events.py:148   ... FROM {table} ORDER BY rowid DESC LIMIT 5000
```
`rowid` یک ستون ضمنی SQLite است. در PG وجود ندارد ⇒ `ORDER BY id DESC`. (این ابزار
تحلیلی است نه کد production، ولی در فاز E باید هم‌زمان مهاجرت کند.)

### ۱۵) JSON داخل `TEXT` (🟡) — ✅ **تصمیم E.6.4: `logs.details` ⇒ `jsonb` (PG)، بقیه TEXT**

| ستون | محل |
|---|---|

| `cartridge_id_state`, `toner_overrides TEXT` | `core/database.py:994`, `:1000` |
| خواندن با `json_extract` | `core/database.py:721-777` |

PG: `JSONB` و عملگرهای `->>`/`->`/`@>`؛ هم‌چنین `_USER_JSON_FIELDS`
(`core/database.py:66`) و `_load_json_list` (`:403`) به `json.loads` پایتونی وابسته‌اند

جزئیات `json_extract` در `docs/sql-paths-inventory.md` (E.0.12) خواهد آمد.

### ۱۶) تراکنش، SAVEPOINT و `executescript` (🟡)

- ۲۱ محل `except sqlite3.*: pass` وجود دارد که همگی «خطای بی‌خطر» را می‌بلعند
  (`docs/sqlite-excepts-inventory.md`). در PG، یک خطا داخل تراکنش، **کل تراکنش** را
  abort می‌کند تا `ROLLBACK`؛ پس همان الگوها بدون SAVEPOINT داده‌ی بعدی را هم
  از دست می‌دهند (نمونه‌ی واقعی: `duplicate column name` در ALTERهای idempotent).
- `core/db/connection.py:140-142` متد `executescript` دارد که در PG معادل ندارد ⇒
  باید به statementهای جدا شکسته شود.

### ۷.۱ یافته‌های جانبی E.4 (ثبت تا در E.6 گم نشوند)

- **الگوی `25P02`:** روی PG هر خطا کل تراکنش را abort می‌کند؛ پس هر حلقه‌ای که
  «خطا را می‌خورد و ادامه می‌دهد» به SAVEPOINT نیاز دارد، و هر تست/ابزاری که چند
  گزارهٔ مستقل می‌زند باید میان آن‌ها `rollback` کند.
- **`details` روی PG نوع `TEXT` داشت** (میراث `0001`)؛ هر عملگر JSON باید صریح
  `::jsonb` می‌شد، وگرنه `operator does not exist: text ->> unknown`. مقدار JSON
  نامعتبر در یک ردیف ⇒ `22P02` (هم‌سنخ «malformed JSON» خود SQLite).
  **تغییر در E.6.4:** `logs.details` حالا `jsonb` است (migration `0004`) ⇒ خطای
  JSON بدفرمت به **زمان نوشتن** منتقل شد و کوئری aggregate دیگر با یک ردیف خراب
  نمی‌سوزد. cast در `json_extract()` عمداً مانده: روی ستون `jsonb` بی‌هزینه است و
  برای چهار ستون JSON دیگرِ پروژه (که TEXT ماندند) همچنان لازم است. تنها ستون‌هایی
  که در SQL JSON می‌خوانند همین دو نقطه بودند؛ معیار و عدد در
  `docs/phase-e-decisions.md` §۶.۴.
- **`GroupingError` (۴۲۸۰۳):** SQLite ستون گروه‌بندی‌نشده را می‌بخشد، PG نه. شاهد
  معکوسش در `tests/test_metrics_pg.py` قفل شده است.
- **گارد یکپارچه بر پراکندگی ترجیح داده شد:** سه اشکال `import_db` (ردیف ۱۱ +
  TD-007 + TD-009) به‌جای سه گارد، یک‌جا و با یک پیام فارسی روشن بسته شد.
- **بکاپِ `import_db` روی PG هیچ کاری نمی‌کند و بی‌صداست:** `_make_backup()`
  (`web/routes/import_db.py:152`) با `os.path.exists(DB_PATH)` شروع می‌شود و اگر
  فایل نباشد `""` برمی‌گرداند؛ روی PG هیچ `logs.db` نیست ⇒ «بکاپ گرفته شد» بی‌صدا
  معادل «بکاپ نگرفته شد». **وضعیت پس از E.6.1:** تنها فراخوان آن (`:399`) در مسیر
  نوشتن است و آن مسیر روی PG زیر گارد بازنشستگی است ⇒ هرگز اجرا نمی‌شود؛ روی
  SQLite رفتار درست دارد و دست‌نخورده مانده. ترجمۀ واقعی `import_db` (فاز F) باید
  `pg_dump` را جانشین کند و نبودِ بکاپ را **خطا** بداند.
  **رفع الگو در E.6.2** (`5570992`): `tools/migrate_timestamps_to_utc.py` حالا روی
  PG بکاپ `pg_dump --format=custom` می‌گیرد و با `pg_restore --list` **تأیید**
  می‌کند؛ بکاپ ناموفق = توقف اجرا، و فایل بی‌اعتبار حذف می‌شود (تا «بکاپ» جعلی
  روی دیسک نماند). `grep -rn pg_dump` دیگر صفر نیست: ابزار + تست.
- **تست‌های سطح‌بالا باید hermetic باشند:** تستی که `DB_BACKEND` را قفل نمی‌کرد
  بی‌صدا به SQLite مخزن افتاد و `logs.db` را نوشت؛ فایل با بازتولید مهاجرت E.3.5
  **بایت‌به‌بایت** بازگردانی شد (sha256 با شاهد `logs.db.e3-manifest.json` یکسان).
  پس هر تست PG که توابع سطح‌برنامه صدا می‌زند: `mock.patch.dict(DB_BACKEND/PG_DSN)`
  + `cwd` موقت + تأیید حضور ردیف در همان PG.
