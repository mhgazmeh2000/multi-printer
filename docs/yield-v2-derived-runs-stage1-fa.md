# مرحلهٔ ۱ — نتیجهٔ نمونهٔ محلی مرزهای تراکنشی run

## تصمیم

**نتیجهٔ محلی مثبت است و نمونه ارزش رفتن به آزمون کپی واقعی را دارد؛ آمادهٔ تولید نیست.**

این مرحله شامل یک نمونه و یک دور اصلاح مسیر خواندن بود. صحت آزمون‌شده و هدف
محلی خواندن پاس شدند. هزینهٔ نوشتن و فضا واقعی است و پنهان نشده؛ پذیرش این
هزینه برای محیط واقعی هنوز به نرخ ingestion، بودجهٔ مورد تأیید و آزمون کپی نیاز دارد.

هیچ فایل اجرایی در `core/`، migration برنامه، schema تولید، سرویس یا تنظیمات
سرور کاربر تغییر نکرد. هیچ PR، merge، push یا استقرار در این مرحله انجام نشد.
ساخت نمونه مجوز تغییر کپی مستقل ویندوز را هم نمی‌دهد.

## چه چیزی ساخته شد؟

- `tools/sql/yield_run_prototype.sql`: جداول مرز/وضعیت/نسخه، ایندکس همسایگی و
  triggerهای PostgreSQL برای INSERT، UPDATE، DELETE و TRUNCATE.
- `tools/yield_run_prototype.py`: ساخت منبع آزمایشی، build اتمیک با توقف صریح
  نویسندگان، reader یک-statement با fallback و benchmark محلیِ قابل‌بازتولید.
- `tests/test_yield_run_prototype.py`: ۱۷ آزمون اختصاصی PostgreSQL با کلاستر متعلق
  به خود تست؛ ورودی DSN خارجی ندارد.
- `docs/evidence/yield-run-prototype-stage1.json`: شواهد عددی کامل سه workload
  مصنوعی؛ فاقد ردیف، IP واقعی، credential یا dump خصوصی.

این‌ها **ابزار و نمونهٔ آزمایشگاهی‌اند، نه پیاده‌سازی متصل به برنامه**. مسیر
`_load_interval_snapshots` عوض نشده و SQLite همچنان مسیر قبلی را دارد.

### نگهداری و هم‌زمانی

قفل‌های تراکنشی بر مبنای slot هستند، نه یک قفل سراسری برای کل fleet. trigger
BEFORE ROW نسخهٔ ردیف پایدار وضعیت slot را تغییر می‌دهد؛ ردیف وضعیتِ slot خالی
حذف نمی‌شود. ترتیب قفل قدیم/جدید هر ردیف ثابت است، ولی deadlock بین statementهای
چنداسلاتی همچنان ممکن است و باید با retry کل تراکنش مدیریت شود.

triggerهای AFTER STATEMENT با transition table، موقعیت‌های قدیم/جدید و همسایه‌ها
را از تصویر نهایی statement می‌گیرند. ردیف تغییرکرده، successor، مرزهای حذف‌شده
و tail دوباره محاسبه می‌شوند؛ از ترتیب رخداد trigger ردیفی فرضی استفاده نشده است.
در REPEATABLE READ، نویسندهٔ دارای snapshot کهنه روی slot نسخه‌خورده با 40001
رد می‌شود؛ صرفاً منتظر قفل‌ماندن و سپس نوشتن با snapshot قدیمی مجاز نیست.

reader وضعیت آماده/نسخه، آخرین مرزها و payload اصلی را در **یک SQL statement**
می‌خواند. نسخهٔ نامعتبر، marker غایب یا وضعیت unready باعث استفاده از SQL مرجع
می‌شود، نه دادهٔ مشتق کهنه. نبود خود schema در این ابزارِ متصل‌نشده پشتیبانی
نمی‌شود؛ انتخاب مسیر در نبود schema بخشی از ادغام آیندهٔ برنامه است.

### همان یک دور اصلاح

نسخهٔ نخست با وجود سرعت حدود ۰٫۳ ثانیه، در join نهایی هنوز Seq Scan روی تمام
۲٫۱۲ میلیون snapshot داشت. در دور اصلاح، دریافت payload به lookup محدودشدهٔ
LATERAL با PK تبدیل شد. معنای آن با یکتایی id تغییر نمی‌کند.

در actual plan نهایی، تنها دسترسی فعال به جدول snapshot، lookup PK با یک ردیف
در هر loop است: ۳۸٬۴۰۰ / ۱۹٬۲۰۰ / ۹۶ loop در سه workload. شاخهٔ سنگین مرجع
هنگام ready بودن اجرا نشد. در workload مرز متراکم، ایندکس مرزها فقط ۴۰۰ ردیف
در هر slot خواند. برای جدول کوچک ۴۸ مرزیِ workload idle، Seq Scan کوچک روی خود
جدول مرزها انتخاب شد؛ این با اسکن تاریخچهٔ اصلی فرق دارد.

## آزمون صحت

اجرای نهایی همهٔ `tests/test_yield*.py` و `test_startup_and_fast_pull.py`:

**۱۵۲ تست پاس، ۴۶۹ subtest پاس، صفر failure و صفر skip.**

آزمون‌های PostgreSQL اختیاری نیز DSN یک دیتابیس موقت جدید `printguard_test_*`
داشتند؛ `.env` عملیاتی وجود نداشت. دو کلاستر متعلق به harness/test پس از اجرا
خاموش و حذف شدند. هشدار کلید پیش‌فرض توسعه دیده شد؛ هیچ سرویس برنامه اجرا نشد.
این نتیجه مربوط به مجموعهٔ yield/startup است، **نه کل suite پروژه**.

گارد تقسیم تست‌ها نیز پاس شد: ۱۰۳۷ TestCase در مسیر unittest و همان ۱۰۳۷ مورد
در نمای جمع‌آوری pytest؛ ۱۷ آزمون تابعی نمونه با marker `pytest_only` در مسیر
اختصاصی جمع‌آوری شدند. نصب `pgserver==0.1.4` فقط به job لینوکسی CI اضافه شد تا
این آزمون‌ها به‌دلیل نبود وابستگی خاموش نمانند؛ requirements برنامه و job ویندوز
تغییر نکردند. **این تنظیم آماده شده، ولی GitHub Actions هنوز برای این تغییرات اجرا نشده است.**

smoke ابزار با متغیرهای ارثی PGHOSTADDR/PGSERVICE/PGPORT ساختگی موفق بود. import
فایل تست بدون pgserver نیز برای unittest ایمن است؛ نبود وابستگی در محیط توسعه
باعث skip صریح آزمون‌های pytest می‌شود، نه خرابی discovery یا اتصال به DSN دیگر.

آزمون‌های اختصاصی موارد زیر را با oracle مستقل و SQL جاری مقایسه کردند:

- کل مرزهای تاریخی، previous_id هر مرز و tail همهٔ slotها؛ نه فقط آخرین ۴۰۰ run.
- tuple کامل خروجی با ترتیب واقعی، limitهای ۰/۱/۳/۴۰۰/۱۰۰۰، فیلتر رنگ mixed-case
  و slot مستقیم در مقابل bulk.
- INSERT چندردیفی نامرتب، UPDATE/DELETE گروهی، backfill، تغییر id و جابه‌جایی slot.
- NULL/empty، پذیرش/منبع/هویت، rollback شمارنده، idle طولانی و بیش از ۴۰۰ run.
- UPSERT، TRUNCATE، rollback تراکنش، build متوقف‌شده و خطای تزریق‌شده در نگهداری؛
  خطای نگهداری مانع commit ردیف اصلی شد.
- دو نویسندهٔ یک slot با مشاهدهٔ واقعی lock wait؛ RC با commit سازگار و RR با
  serialization failure و retry کل تراکنش.
- ایجاد slot پس از snapshot نویسندهٔ RR؛ خطای مورد انتظار و retry موفق.
- جابه‌جایی گروهی slotها توسط دو نویسنده در RC و RR، با بودجهٔ retry محدود.
- deadlock عمدی در RC و RR، مشاهدهٔ 40P01، rollback قربانی و بازاجرای **هر دو**
  نوشتن تراکنش قربانی؛ نه فقط statement آخر.
- reader با snapshot ثابت در حین جابه‌جایی commitنشده و پس از commit نویسنده.
- actual plan بدون اسکن تاریخچه هنگام ready بودن.

این‌ها شواهد آزمون‌اند، نه اثبات صوری تمام interleavingهای ممکن یا همهٔ
نسخه‌ها/localeهای PostgreSQL. bypass کردن triggerها، تغییر مستقیم جدول مشتق
یا session_replication_role خاص، خارج از تضمین این نمونه است.

## اندازه‌گیری نهایی

هر workload یک کلاستر تازهٔ محلی روی Linux با PG **16.2** داشت؛ نه PG17.5 ویندوز.
۲٬۱۲۶٬۳۰۰ ردیف مصنوعی، ۴۸ slot، shared_buffers=128MB، work_mem=4MB، parallel workers
برابر ۲؛ fsync، synchronous_commit و full_page_writes روشن. سقف هر statement
۳۰ ثانیه بود؛ زمان کل ابزار طبعاً بیشتر است.

جدول‌ها از نوع‌های مرتبط با loader در migration 0001 استفاده می‌کنند؛ پهنای
متن/توزیع داده/دیسک واقعی را شبیه‌سازی کامل نمی‌کنند. warm خواندن پس از SELECT
مرجع و مقایسه انجام شده؛ **cold-cache یا صدک تأخیر API نیست**.

| workload | تعداد مرز | endpoint | SELECT مرجع، ثانیه | پنج خواندن گرم نمونه، ثانیه | build و نصب، ثانیه |
|---|---:|---:|---:|---|---:|
| هر run حدود ۱۰۰ poll | 21,264 | 38,400 | 6.7484 | 0.1207 / 0.1288 / 0.1443 / 0.1575 / 0.1443 | 10.1949 |
| هر poll یک مرز | 2,126,300 | 19,200 | 8.3324 | 0.0680 / 0.0733 / 0.0711 / 0.0767 / 0.0550 | 19.4474 |
| idle؛ یک run در هر slot | 48 | 96 | 6.5635 | 0.0016 / 0.0016 / 0.0015 / 0.0016 / 0.0017 | 9.4442 |

در هر سه، خروجی کامل با SQL مرجع برابر بود: قبل از ingestion، پس از ۲۰۰ INSERT
و پس از عملیات گروهی. تمام ۱۵ خواندن گرم زیر هدف پیشنهادی محلی ۲ ثانیه بودند.
این نتیجه هیچ زمان یا درصد بهبودی را برای کپی ویندوز/تولید ثابت نمی‌کند.

### هزینهٔ نوشتن: افزایش دارد

هر ستون زیر p95 نمونهٔ **۲۰۰ تراکنش INSERT تک‌ردیفی commitشده، تک‌اتصالی** است.
مرجع قبل از ایندکس/trigger جدید و نمونه پس از نصب اندازه‌گیری شده؛ دو فاز ترتیب
ثابت دارند و آزمون بار پایدار/production p95 یا آزمایش هم‌زمان چندنویسنده نیستند.

| workload | p95 مرجع، ms | p95 نمونه، ms | WAL مرجع/نمونه برای ۲۰۰ INSERT، bytes |
|---|---:|---:|---:|
| ۱۰۰ poll/run | 0.4145 | 1.4922 | 70,264 / 143,912 |
| هر poll مرز | 0.2712 | 1.2511 | 70,264 / 877,048 |
| idle | 0.3915 | 1.4013 | 70,264 / 144,032 |

WAL به page state و full-page image/checkpoint نیز وابسته است؛ این نسبت‌ها
ضریب ثابت write amplification تولید نیستند. نمونهٔ INSERT به همهٔ slotها سر
می‌زند، اما همهٔ الگوهای واقعی نگهداری را نمایندگی نمی‌کند.

یک statement با ۱۰۰۰ ردیف برای هر عملیات، با commit واقعی (فقط یک نمونه؛ نه p95):

| workload | UPDATE مرجع/نمونه، ms | DELETE مرجع/نمونه، ms | INSERT بازیابی مرجع/نمونه، ms |
|---|---:|---:|---:|
| ۱۰۰ poll/run | 5.46 / 59.78 | 1.10 / 33.20 | 44.35 / 94.70 |
| هر poll مرز | 5.34 / 70.21 | 1.11 / 33.76 | 45.21 / 95.26 |
| idle | 4.67 / 66.36 | 1.29 / 42.41 | 46.68 / 100.53 |

پس «خواندن سریع‌تر» رایگان نیست. به‌خصوص retention یا تغییر گروهی میلیون‌ردیفی
هنوز benchmark نشده؛ بودجهٔ نوشتن، deadlock/retry تحت بار پایدار و نرخ واقعی
snapshot باید پیش از پذیرش عملیاتی تعیین شوند. این مرحله ادعای پاس‌شدن بودجهٔ
نامشخص نوشتن ندارد.

### فضا

اندازهٔ اولیهٔ منبع با ایندکس‌های قبلی تقریباً ۳۱۰٫۲ MiB بود. در پایان نصب/build:

- منبع با ایندکس همسایگی و بloat کوچک ناشی از آزمون: تقریباً ۴۰۷٫۹ MiB.
- مرزها: حدود ۳٫۴۳ MiB در حالت ۱۰۰ poll/run، **۳۶۶ MiB** در حالت هر poll مرز،
  و ۴۸ KiB در idle.
- مجموع افزایش اندازهٔ relationها نسبت به ابتدا: حدود **۱۰۱٫۲ / ۴۶۳٫۷ / ۹۷٫۸ MiB**
  در سه workload. این شامل تخمین فضای موقت ساخت/WAL، فضای اوج یا کل کلاستر نیست.

این اعداد برآورد نیاز دیسک واقعی سرور نیستند؛ توزیع مرز و پهنای ردیف واقعی
هنوز نامعلوم‌اند. هر سه کلاستر benchmark پس از پایان حذف شدند.

## بازتولید توسعه‌دهنده

فقط در محیط توسعهٔ بدون `.env` عملیاتی و با وابستگی‌های اختیاری
`psycopg[binary]` و `pgserver`:

```sh
python -m tools.yield_run_prototype --rows 2126300 --slots 48 --plateau-polls 100 --repeats 5
python -m tools.yield_run_prototype --rows 2126300 --slots 48 --plateau-polls 1 --repeats 5
python -m tools.yield_run_prototype --rows 2126300 --slots 48 --plateau-polls 3000000 --repeats 5
DB_BACKEND=sqlite PG_DSN='' python -m pytest -q tests/test_yield_run_prototype.py
```

ابزار DSN نمی‌پذیرد، settings/.env برنامه را import نمی‌کند، متغیرهای libpq ارثی
را کنار می‌گذارد و دیتابیس/کلاستر خصوصی خودش را می‌سازد. helperهای نصب قبل از DDL
نام دیتابیس `printguard_test_*` را بررسی می‌کنند؛ این guard به‌تنهایی جای مالکیت
کلاستر را نمی‌گیرد. فایل SQL خام را نباید روی تولید اجرا کرد.

## مرز این تحویل و قدم بعد

مرحلهٔ ۱ در همین نقطه بسته است؛ آزمایش محلی دیگری بدون دلیل تازه لازم نیست.
پیشنهاد ادامه فقط **آزمون کنترل‌شدهٔ نمونه روی کپی E** است و نیاز به تأیید جداگانه
برای ساخت/نوشتن جداول و triggerهای آزمایشی دارد. فعلاً فرمانی برای سرور صادر نشده.

پیش از آن بستهٔ آزمایش باید هویت کلاستر مستقل، schema/types/indexes واقعی، rollback
و پاک‌سازی اشیای آزمایشی را کنترل کند. برای بازنمایی حجم واقعی، دادهٔ کپی محلی
کاربر استفاده می‌شود؛ انتقال dump یا ردیف خام به این مخزن لازم نیست.

مواردی که هنوز انجام نشده‌اند:

- صحت/زمان/هزینه/فضای واقعی روی PG17.5 ویندوز؛ آستانهٔ قابل‌قبول نوشتن با نرخ واقعی.
- crash/restart و restore نمای مشتق، role/permission و مسیرهای bypass کنترل‌شده.
- ادغام با برنامه، retry کامل تراکنش در مسیرهای لازم، انتخاب مسیر در نبود schema،
  feature flag، migration رسمی و آزمون rollout/rollback.
- بررسی CI/کل suite، PR و تأیید مستقل merge/استقرار تولید.

تا آن زمان `deployment_ready=false` باقی می‌ماند. این نتیجه نه تأیید ETA در
چرخه‌های واقعی مصرف است، نه اعلام پایان کل پروژه.
