# اصلاح عملیاتی estimator v2 پس از بازپخش دادهٔ واقعی

## دامنه و ایمنی

این تغییر داده، migration، reset یا ترمیم تاریخچه ندارد. فایل export عملیاتی، IPهای واقعی و DSN وارد Git نشده‌اند. آزمایش‌ها روی SQLite موقت/حافظه‌ای و PostgreSQL محلیِ جداگانه اجرا می‌شوند؛ سرور عملیاتی تغییر نکرده است.

## علت‌ها و اصلاح‌ها

### ۱. بازگشت شمارنده پس از excursion

در نمونهٔ HP، صفر شمارنده با `valid=1` میان شمارنده‌های حدود ۶۰ هزار ثبت شده بود. صرفاً شکستن سری در افت شمارنده کافی نبود: بازگشت به مقدار قبلی در بخش جدید به‌عنوان ده‌ها هزار صفحه چاپ تفسیر می‌شد.

`segment_readings` اکنون high-water شمارنده را نگه می‌دارد. اگر شمارندهٔ پایین‌آمده با پرشی بزرگ‌تر از `max(100, high_water*0.5)` به high-water قبلی برسد، بخش جدید `counter_recovery` آغاز می‌شود. صفر به‌طور کلی حذف نمی‌شود؛ دستگاه تازه و reset واقعی با رشد تدریجی همچنان قابل یادگیری‌اند. تعویض chip دامنهٔ high-water را از نو آغاز می‌کند.

این یک قاعدهٔ محافظه‌کارانهٔ پیوستگی است، نه تشخیص قطعی reboot یا اثبات نامعتبر بودن هر پرش بزرگ. اگر high-water در دادهٔ ورودی موجود نباشد، این قاعده نمی‌تواند آن را بازسازی کند.

### ۲. پنجرهٔ تاریخچه بر حسب تغییرات، نه تعداد poll

مسیر قبلی فقط ۴۰۰ poll آخر را می‌خواند. برای دستگاهی که روزها درصد ثابت دارد، تمام افت‌های قبلی از ورودی محاسبه خارج می‌شدند؛ سابقه در دیتابیس بود ولی estimator آن را نمی‌دید.

`_load_interval_snapshots` به‌صورت مشترک در مسیر live و status به کار می‌رود:

- run بر اساس درصد خام/پردازش‌شده، منبع، اعتبار، علت رد، هویت کارتریج و حضور شمارندهٔ رنگی تعریف می‌شود؛ rollback شمارنده نیز مرز run است.
- ابتدا و انتهای حداکثر ۴۰۰ run آخر هر slot خوانده می‌شوند: حداکثر ۸۰۰ endpoint، با ترتیب زمانی مبتنی بر id.
- poll تکراری در یک run، افت درصدهای قبلی را از پنجره خارج نمی‌کند.
- این پنجره هنوز محدود است: بیش از ۴۰۰ تغییر هویت/اعتبار/درصد می‌تواند شواهد قدیمی را کنار بزند. تاریخچهٔ حذف‌شده یا غایب از export قابل بازسازی نیست.
- query در DB از window function استفاده می‌کند و تاریخچهٔ slotهای منتخب را اسکن می‌کند؛ محدودیت تعداد خروجی به معنی هزینهٔ ثابت query نیست. قبل از استقرار باید latency روی کپیِ با اندازهٔ واقعی دیتابیس سنجیده شود.

### ۳. حفظ مرجع مستقل کاتالوگی

اگر lookup فعلی کاتالوگ با هویت ناقص match نشود ولی `yield_source=catalog` و ظرفیت ذخیره‌شده معتبر باشد، همان مرجع به‌عنوان prior کاتالوگی حفظ می‌شود. lookup معتبر فعلی اولویت دارد. مقدار `auto_learn`/`cycle_learn` یا پروفایل خود دستگاه همچنان prior مستقل محسوب نمی‌شود.

این تغییر منشأ تاریخیِ برچسب catalog را مستقلاً اثبات یا کل کاتالوگ را تصحیح نمی‌کند؛ به برچسب ذخیره‌شده اعتماد محدود می‌کند.

### ۴. قرارداد خروجی عملیاتی

در v2 غیر forced، `yield_per_page`، `yield_source` و `confidence` با همان تصمیمی هماهنگ‌اند که ETA و CI را تولید می‌کند. اطلاعات قبلی حذف نشده‌اند و با نام‌های زیر برمی‌گردند:

- `stored_yield_per_page`
- `stored_yield_source`
- `stored_confidence`

فیلدهای `interval_confidence` و `estimator` نیز اضافه شده‌اند. مقدار estimator یکی از `v2`، `legacy` یا `forced_estimate` است. در حالت legacy/forced، ظرفیت عملیاتی و ETA از مقدار ذخیره‌شده پیروی می‌کنند؛ فیلدهای interval همچنان نتیجهٔ سایهٔ v2 هستند. `sample_count` و `learned_at` همچنان اطلاعات ذخیره‌شده‌اند و نباید با تعداد plateauهای تصمیم جدید اشتباه شوند.

## بازپخش فایل export

بدون اتصال به دیتابیس عملیاتی:

```text
python tools/yield_diagnostic_replay.py --input yield-v2-diagnostic.json --output yield-v2-replay-result.json
```

این ابزار فقط یک SQLite حافظه‌ای می‌سازد. حتی با `DB_BACKEND=postgresql` و PG_DSN در محیط، از آن اتصال استفاده نمی‌کند. resolver کاتالوگ از checkout/تنظیمات فعلی استفاده می‌کند؛ بنابراین خروجی، بازسازی قطعی پیکربندی قدیمی سرور نیست. فایل ورودی و خروجی حاوی اطلاعات ناوگان‌اند و نباید commit شوند.

### نتیجهٔ نمونهٔ واقعی روی کپیِ فقط‌خوانده‌شده

| مورد | نتیجهٔ قبل | نتیجهٔ اصلاح‌شده با همان export |
|---|---|---|
| A: HP با excursion شمارنده | ظرفیت ۵۶۸٬۵۲۵، ETA برابر ۱۵۳٬۵۰۲ | ظرفیت ۹۵۲، CI برابر ۷۳۳ تا ۱٬۳۵۶، ETA برابر ۲۵۷، confidence پایین |
| B: مرجع کاتالوگی ذخیره‌شده | prior پیش‌فرض ۲٬۰۰۰ | prior کاتالوگی ۲۳٬۸۰۰، confidence پایین |
| C: ۴۰۰ poll با درصد ۵۶ ثابت | prior پیش‌فرض ۲٬۰۰۰ | در همین export همچنان ۲٬۰۰۰؛ ولی confidence عملیاتی دیگر high قدیمی نیست |

**اعداد بالا برآوردند، نه ظرفیت واقعی اندازه‌گیری‌شده یا تأیید ETA.** در مورد C، snapshotهای قدیمی‌تر داخل export نیستند؛ از نمونه‌های نسبت مصرف برای جعل snapshot یا prior استفاده نشده است. رفع eviction با fixture مستقل شامل افت‌های قدیمی و ۱۵۰۰ poll ثابت آزموده شده، نه با ادعای بازیابی دادهٔ غایب.

برای ۱۲۰۰ snapshot همین export، endpointها و تصمیم‌ها روی PostgreSQL واقعی محلی و SQLite دقیقاً برابر شدند (۲۹ endpoint). هیچ DSN عملیاتی در این بررسی استفاده نشد.

## اعتبارسنجی

- تست‌های جدید: `tests/test_yield_v2_operational.py`؛ counter recovery، صفر معتبر/reset واقعی، plateau history، ثبات CI در pollهای کاملاً تکراری، سقف endpoint، برابری query کلی/تکی، حفظ مرزهای اعتبار/هویت/manual reset، اولویت کاتالوگ، API و forced/legacy، و استقلال ابزار replay از DSN.
- تست PostgreSQL opt-in با `YIELD_TEST_PG_DSN` فقط دیتابیس با پیشوند `printguard_test_` را می‌پذیرد و TEMP table می‌سازد. در اجرای معمول بدون DSN رد می‌شود؛ جداگانه روی PostgreSQL محلی اجرا و پاس شد. pgserver فقط ابزار آزمایش محلی بود و به وابستگی‌های برنامه اضافه نشده است.
- تست قبلی startup/cache به قرارداد جدید ۴۰۰ run / حداکثر ۸۰۰ endpoint به‌روزرسانی شده است؛ صحت cache، عدم تخریب با mutation پاسخ و invalidation فوری manual reset همچنان آزموده می‌شوند.
- golden مستقل: ۱۱ پاس؛ benchmark مصنوعی ۸۰۰ کارتریج: تمام gateها پاس، MAPE برابر ۵٫۰۶٪ و idle drift صفر. این‌ها اثبات دقت روی ناوگان واقعی نیستند.
- benchmark محلی PostgreSQL با ۲۰۰ هزار رکورد مصنوعی و ۴۸ slot: query کلی حدود ۰٫۷۷ ثانیه، query یک slot حدود ۰٫۰۳ ثانیه؛ در آزمایش ۲ میلیون رکورد / ۴۸ slot، query کلی ۷٫۶۴ ثانیه و query یک slot ۰٫۲۴ ثانیه طول کشید. این عدد SLA سرور عملیاتی نیست و هزینه با تاریخچه رشد می‌کند. بنابراین PR باید تا بررسی/بهینه‌سازی هزینهٔ fleet query پیش‌نویس بماند و آمادهٔ merge/استقرار تلقی نشود.

- آزمون‌های متمرکز yield: ۱۲۲ تست، ۱۲۱ پاس و یک skip اختیاری PostgreSQL. تست PG جداگانه اجرا و پاس شده است.
- pytest-only: ۳۳ پاس؛ guard شمارش تست‌ها: ۱۰۲۹ تست در هر دو مسیر، بدون دوبارشماری.
- اجرای همان ۱۵ تست جدید روی baseline: ۶ failure و ۴ error (از جمله نبود helper/ابزار جدید)، ۱ skip؛ روی تغییرات ۱۴ پاس و ۱ skip، به‌علاوهٔ اجرای جداگانهٔ تست PG.
- baseline کامل: ۱۰۱۴ تست، ۸ failure، ۲ error و ۷۵ skip. اجرای کامل نهایی با ۱۰۲۹ تست همان ۱۰ هویت خطا/شکست را داشت: ۸ failure، ۲ error و ۷۶ skip (یک skip اضافه مربوط به تست PG اختیاری است). هویت تک‌تک خطاها/شکست‌ها با baseline مقایسه و برابر تأیید شد. خطاهای قدیمی در backup_pg، cutover_readiness و jsonb_columns هستند؛ «همهٔ full suite سبز است» ادعا نمی‌شود.

## استقرار

این بسته به migration یا reset یادگیری نیاز ندارد. تا تکمیل CI، بازبینی PR و سنجش کارایی روی کپی دیتابیس کامل، روی سرور pull/restart انجام نشود. merge این PR نیازمند تأیید جداگانه است. پس از merge، استقرار به commit ادغام‌شده و بررسی دوبارهٔ `/api/yield/status` انجام می‌شود؛ rollback کد جایگزین حذف تاریخچه نیست.
